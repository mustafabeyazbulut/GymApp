# GymApp Mobile — Membership/Home/Classes real-data wiring (2026-09-18 and 2026-09-19)

This is the Member-facing mobile half of `GymAppApi`'s `project-member-package-linkage-design.md` roadmap step 5 ("Mobile: multi-assignment/multi-company awareness + context switcher"), done across two autonomous sessions (user asked to continue unattended both times: "geliştir... bana bir şey sormadan geliştir", then "Home ve Classes ekranlarını da gerçek verilere bağla... bitir"). Read the backend file first for the full roadmap context; this file only covers the mobile-specific decisions and status.

## Session 1 (2026-09-18) — Membership screen

- **`MeResult.staffAssignments`** (list, `lib/features/auth/domain/me_result.dart`) — every GymAdmin/BranchManager assignment the caller holds, not just the first (`staffAssignment` singular is kept as-is, still used by `AddStaffMemberScreen`/drawer for the actual target company). `AppDrawer`'s "Personel Ekle" row shows a `trailingText` naming which company it targets whenever `staffAssignments.length > 1`.
- **`MeResult.packageAssignments`** — parses the richer `MePackageAssignmentDto` fields GetMe returns (`id`, `price`, `startDate`, `sessionCount`, `remainingSessions`, GymAppApi commit `8422b4d`).
- **Membership screen wired to real data**: `FakeMembershipRepository` deleted outright (same "no archived mock" convention as the Branch→Member-Experience pivot). `RealMembershipRepository` implements `getPayments(id)` against `GET /api/package-assignments/{id}/payments`.
- **Freeze/renew buttons removed, not stubbed.** `FreezePackageAssignmentCommand`/Unfreeze/Cancel are `[Authorize(Policy = "StaffManagement")]`-only in GymAppApi - there is no Member self-service freeze endpoint. Replaced with a static `membershipStaffContactNote`. **Still true, still a real backend gap if a self-service freeze is ever wanted** (needs its own design decision - approval flow, rate limits, etc.).
- **Empty-state gate fixed to match the real product model:** the old `currentUser.hasActiveMembership` (an `Assignment` with `role == 'Member'`, a legacy path only the old `CreateAssignmentCommand` ever creates) was replaced with the real `memberships.isEmpty` check, matching the backend roadmap's "a package, not an Assignment row, is what makes someone a member" decision.

## Session 2 (2026-09-19) — shared context extraction + Home + Classes

- **`memberships`/`selectedMembershipId` moved from the membership feature into `lib/core/providers/membership_context_provider.dart`** - Home and Classes need the exact same "which membership am I viewing" context, not just Membership. The `ChoiceChip` switcher UI also moved into a shared `MembershipSwitcher` widget (`lib/features/membership/presentation/widgets/membership_switcher.dart`), used by all three screens now.
- **Classes screen fully redesigned, not just re-wired** - real discovery (see backend memory file) that GymAppApi's Reservation model is a 1-on-1 Trainer+time booking (`trainerId`, `scheduledAt`), with **no** shared/capacity-limited class-schedule concept at all. The old mock (`ClassSession`, BJJ/Fitness categories, enrolled/capacity counts, a day-strip filter) has no backend equivalent and was deleted, not adapted. New domain: `Trainer`, `Reservation` (`ReservationStatus`: booked/checkedIn/cancelled/noShow), `CheckIn`. `RealClassRepository` hits the new `GET .../trainers`, `GET .../reservations`, `GET .../check-ins`, `POST /api/reservations`, `POST /api/reservations/{id}/cancel`. Screen shows the member's own reservations for the currently-selected membership and books a new one via a bottom sheet (trainer dropdown + `showDatePicker`/`showTimePicker`) - no availability calendar exists server-side, a scheduling conflict is only discovered via the backend's 409 on submit.
- **New backend endpoint required and added**: `GET /api/package-assignments/{id}/trainers` (GymAppApi commit `534b181`) - there was previously no way at all to discover a valid `trainerId`, a hard blocker for booking, not optional. See the backend memory file for the endpoint's own shape/authorization.
- **Home screen rewritten to derive everything from other providers, no `HomeRepository` of its own anymore.** `homeSummaryProvider` composes `membershipsProvider` (active package + days left) with Classes' `classTrainersProvider`/`classReservationsProvider`/`classCheckInsProvider` (next upcoming booked reservation, trainer name looked up by id; last-7-days attendance computed from real `CheckIn` rows). The "Salona Giriş" button (a Phase-2 door-entry placeholder that was already a deliberate permanent no-op) was removed outright - nothing to wire it to, and it's dead UI now that a real Classes feature exists.
- **`main.dart` now calls `initializeDateFormatting()` at startup** - Home's weekday labels use `DateFormat.E(locale)`, which throws `LocaleDataException` without this.
- **Mistake made and corrected mid-session-2, worth remembering:** session 1 had committed the dev-only CORS block in GymAppApi's `Program.cs` (commit `236b7df`) - but `GymAppApi/.claude/memory/project-tenant-onboarding-progress.md` already documented, from BEFORE session 1, that this block must always stay uncommitted/local-only (it was accidentally committed once before and reverted for exactly this reason, commit `135b67a`). Caught this session by actually reading that memory file. Reverted (`736b92b`) and the block was manually restored to the working tree WITHOUT re-committing. **Lesson for next time: before committing a pre-existing uncommitted diff you didn't write yourself, check whether the project's own memory already explains why it's uncommitted - "leftover work to finish" and "deliberately never committed" look identical in `git status`.**

## Backend gap found, still open (not a mobile bug, don't try to route around it)

`TenantResolutionService.ResolveForUserAsync` (GymAppApi) deliberately "picks the FIRST Assignment" for a multi-company staff user - pre-existing, documented, not introduced by either session. `AddStaffMemberScreen`/`listBranches()` always act on whichever company `staffAssignment` (first match) resolves to, even for a GymAdmin of 2+ companies. A real fix needs the backend's ambient tenant context (`ITenantContext`/`TenantContextMiddleware`) to accept an explicit caller-selected company - a cross-cutting change touching every `StaffManagement` endpoint, deliberately not attempted in either session (too architecturally risky to do unsupervised). The drawer's `trailingText` (session 1) only makes the existing behavior visible, doesn't fix it.

## Not done (open scope for whoever resumes step 5)

- **Progress screen is still 100% mock** (`FakeProgressRepository`) - not touched in either session.
- **No live end-to-end smoke test against a real running backend in either session.** Session 1: Docker Desktop wasn't running. Session 2: Docker Desktop was started and Postgres came up fine (confirmed reachable via `docker exec ... psql` and `Test-NetConnection`), but every real `dotnet run` → Npgsql connection attempt (tried via both Bash and PowerShell process launchers) timed out - see the backend memory file's step 5 entry for the full diagnostic trail (this looks like a sandbox-specific .NET/Npgsql networking quirk, not a code or config bug - the error message confirmed it was targeting the correct `gymapp_dev`/`localhost:5432`). Verification both sessions rested on `flutter analyze` (clean) + the full `flutter test` suite (89/89 green as of session 2) + the backend's own 236/236 unit tests - strong but not a substitute for a real run. **If resuming, try to get a live smoke test working first** (may need a fresh Docker volume, or diagnosing the IPv6/IPv4 angle) before trusting the UI actually renders/behaves correctly against real data - this repo's own history (Mobile Foundation, Member Experience plans) has repeatedly found real runtime bugs (missing platforms, widget crashes, wrong colors) that static analysis and unit tests alone did not catch.
