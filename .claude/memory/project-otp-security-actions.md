# Post-Real-Auth iteration — current status (2026-09-16)

[[project-real-auth-design]] covers the original Real Auth plan (backend 14/14, mobile 15/15, COMPLETE). Everything below happened in the session(s) after that plan shipped and is the actual current state — in particular it **reverses** that file's line 113 ("Auth method: email-or-phone + password. No SMS OTP anywhere... matches the already-approved login mockup exactly (single-step, no OTP screen)"). That is no longer true: registration is now phone/email OTP-verified, and three more self-service account actions also require an OTP code. Trust this file over that line if they conflict.

## What changed, in order

1. **Register redesigned to require OTP verification** (both repos). Two-step flow: `POST /api/auth/register/request-otp` (sends a 6-digit code to phone, and email if given) → `POST /api/auth/register/complete` (verifies both codes, creates the account, returns tokens). Backend: `PendingContactVerification` entity (not FK-linked to `User` — exists independently, upserted per `(Channel, Target)`, 10-min expiry, 60s cooldown, 5-sends/hour rate limit, 5 wrong-attempt cap). Mobile: `intl_phone_field` for country-code phone entry, digit-only OTP inputs, password-confirmation field added to Register at the same time (user explicitly asked for double-password entry).
2. **Phone normalization** (`IPhoneNumberNormalizer`, backed by `libphonenumber-csharp`, default region "TR") applied to Login/ForgotPassword/ResetPassword identifiers — fixes old accounts registered with inconsistent phone formats (with/without leading 0, with/without country code) all resolving to the same user.
3. **Notifications** — a simple mock-data-only screen + bell icon (moved from where Logout used to sit). Not backed by any real push/notification backend, explicitly scoped that way by the user.
4. **Language switcher** — `PreferredLanguage` on `User` (`PATCH /api/auth/me/language`, "tr"/"en" only), account-synced: mobile's `AppLocale` Riverpod notifier seeds itself from the account's `preferredLanguage` on login (`seedFromAccount`, only if the user hasn't picked a locale locally yet), user can override anytime via the Membership screen's language row.
5. **Self-service temporary account freeze/reactivate** — distinct from the existing membership/package freeze. `User.IsAccountFrozen`. Freezing revokes every active refresh token. **Login is never blocked by a frozen account** — it succeeds, and the mobile app gates all 4 content screens behind `AccountFrozenState` (checked before `EmptyMembershipState`) until reactivated. Design doc: `GymAppApi/docs/superpowers/specs/2026-09-16-account-freeze-design.md`.
6. **OTP-gated the 3 security-sensitive self-service actions** (added after the freeze feature shipped, per explicit user request: "hesabı dondururken de doğrulama koduyla dondursun... hesabı sil de de onay kodu gitsin"). Freeze, reactivate (unfreeze), AND delete-account all now require a 6-digit phone code first:
   - `POST /api/auth/me/freeze/request-otp` → `POST /api/auth/me/freeze {code}`
   - `POST /api/auth/me/unfreeze/request-otp` → `POST /api/auth/me/unfreeze {code}`
   - `POST /api/auth/me/delete/request-otp` → `DELETE /api/auth/me {code}` (body on a DELETE — works fine, ASP.NET Core infers `[FromBody]` for a complex type regardless of HTTP verb)
   - All three reuse `PendingVerificationCodeService` (`GymAppApi.Application.Common.ContactVerification`), extracted from what used to be duplicated rate-limit/attempt-counting logic in `RegisterRequestOtpCommandHandler`/`RegisterCompleteCommandHandler` — this is now the one place that logic lives, always target `ContactChannel.Phone` + `user.Phone` for these three (never email).
   - Mobile: shared `lib/core/widgets/otp_code_dialog.dart` (`showOtpCodeDialog`) — a single 6-digit-entry `AlertDialog` reused by all three flows (freeze via the confirm-then-code dialog chain in `membership_screen.dart`, reactivate via `AccountFrozenState`, delete via the existing "are you sure" dialog then the code dialog).
   - `RealAuthRepository._mapException`'s 401 special-case (surface the backend's own message instead of the generic "wrong password" `InvalidCredentialsException`) now keys off `(method, path)` pairs, not path alone — `DELETE /api/auth/me` needed this because `GET /api/auth/me` (an expired access token, a completely different 401 meaning) shares the same path.
7. **Membership screen visual fixes** (two rounds, both from direct user complaints about polish, not functional bugs):
   - The bottom account-actions area was first built as a flat `TextButton` stack — user explicitly rejected this as inconsistent with the approved mockup and asked for the mockup to be re-read; redone as a hairline-bordered "HESAP" card (rows: language/freeze/delete, chevron-right trailing, tappable) matching the same `Container`+`AppColors.border`+`AppSpacing.radiusLg`+`labelSmall`-eyebrow pattern already used for the Payment History card, with Logout kept as a separate `OutlinedButton` below (matching the mockup's own `.btn2.outline` treatment for "Üyeliği Dondur").
   - Then user said it still wasn't "şık" (elegant) — root cause: the membership summary/payment-history/HESAP cards were all built with `border` only, no `color:` set on their `BoxDecoration`, so they had no visible fill and blended into the scaffold background. **See [[feedback-visual-language]]'s updated card-fill note — this is now a standing rule, not a one-off fix.** Fixed by adding `color: AppColors.surface` to all three cards' decorations, adding a leading icon to each settings row, and `clipBehavior: Clip.antiAlias` so row ripples stay inside the rounded corners.
   - Separately, dialogs (language picker, freeze/delete confirm, the new OTP code dialog) had no `dialogTheme` set at all, so Material3 fell back to `colorScheme.surface` (near-black `AppColors.background`) plus its default elevation-based primary-tint overlay — read as uneven dark blotching toward the rounded corners. Fixed in `lib/core/theme/app_theme.dart` by adding an explicit `dialogTheme`: `backgroundColor: AppColors.surface`, `surfaceTintColor: Colors.transparent`, same hairline-border shape as `cardTheme`. Any new dialog anywhere in the app now gets this automatically — don't hand-roll per-dialog styling.

## Git/repo facts worth knowing

- `GymApp` had **no commits on its GitHub remote at all** until this session — `git push -u origin main` was a first-ever push (the branch's upstream tracking showed `[gone]` beforehand, which just meant "no remote branch exists yet," not an error to investigate).
- `GymAppApi/Presentation/GymAppApi.WebApi/Program.cs` carries a permanent **uncommitted, dev-only CORS block** (`AddCors`/`UseCors("DevClients")`, Development-environment-gated) needed for live Chrome testing against `localhost`. This is intentional and must never be committed — every commit in this repo excludes it (`git add -A -- ':!Presentation/GymAppApi.WebApi/Program.cs'` or equivalent), and it must be `git stash`ed before any operation that refuses to run with unstaged changes (e.g. `git filter-branch`).
- A prior Haiku-implemented commit (`bdf014e`, "Make RegisterCommand transactional") still had a `Co-Authored-By: Claude Haiku 4.5` line that survived an earlier cleanup pass — caught before push this session via a full `git log origin/main..HEAD --format='%B' | grep -i claude` sweep, fixed with `git filter-branch --msg-filter 'sed "/Co-Authored-By: Claude/Id"' -- origin/main..HEAD` (user re-approved the same destructive-git-classifier prompt as last time). **Lesson: a targeted-range filter-branch fix earlier in a session does not guarantee the WHOLE unpushed range is clean — always grep the full `origin/main..HEAD` range right before any push, not just the range you think you fixed.**
